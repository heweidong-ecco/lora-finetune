## 一 · 要解决的问题

本库 `CLAUDE.md` §一 的原话是：

> *「一直调参只是改变曲线和数值，**无法改变输出结果的质量**」*

**这句话本身，本库从来没有验证过** —— 因为**从来没有记录过输出质量**。
E01~E03 只有 loss，`results/` 里那份评测又不可用（见 §二）。

**E05 就是把"输出质量"变成一个可记录的量。**

## 二 · ⚠️ 先看已有的教训：那次评测为什么废了

`results/` 里有一份 50 条的评测（基座 vs 微调），**结论不可用**。实测复算：

| 状态 | 条数 |
|---|---|
| 两边回答**都空** | **24** |
| 仅一边空 | 7 |
| ✅ **两边都非空（唯一可比）** | **19 / 50** |

裁判判决里 **23 条平局，其中 20 条是 `both_bad`（都答不出来）**。
抽样一条可用的，两边回答**逐字相同**。

**✅ 原因已确认** —— 证据就在本仓库自己的文件里。见 `scripts/eval/batch_evaluate.py` 第 63–66 行：

```python
run_evaluation(
    "data/my_test_dataset.json",
    "qwen3:8b",                # 基座模型
    "qwen3:8b",                # 微调模型（需要先用 Ollama 加载 LoRA）
    "evaluation_results.json"
)
```

**两边传的是同一个模型名 `qwen3:8b`** —— 注释自己就写着「需要先用 Ollama 加载 LoRA」，
**但那一步当时从未做**（适配器尚未导入 Ollama）。

👉 **那次评测比的是「qwen3:8b vs qwen3:8b」** —— 两边逐字相同是**必然结果**，与微调效果**完全无关**。

> 📌 `final_judgment.json` 里自带 `errors: 21` 字段，**脚本自己标出来了**，
> 只是当时没人据此判定「整次评测无效」。
> 完整分析见 `results/readme说明.md`。

### 👉 所以 E05 必须带三道检查

| # | 检查 | 为什么 |
|---|---|---|
| 1 | **每条都要验两个回答非空** | 空的标 `ERROR`，**不计入胜率分母** |
| 2 | **同一条 prompt 两边输出若逐字相同 → 报警** | 提示两个端点可能其实是同一个模型（adapter 没加载 / 打错端口） |
| 3 | **平局要分类** | 区分「都好」(`both_good`) 和「都差」(`both_bad`)——**`both_bad` 不能算打平** |

## 二之二 · 可复用的评估口径（来自本库既有的评测脚本）

> 本库 `scripts/eval/` 下已有一套完整评测口径，E05 **沿用它，不另起一套**。

### 裁判 Prompt 的五个设计原则

| 原则 | 做法 |
|---|---|
| **角色分离** | 明确「你是裁判，不是助手」——`You are a JUDGE, not an assistant. Do NOT answer the instruction.` |
| **标准前置** | 先列评判维度，再给数据 —— **准确性 / 完整性 / 清晰度 / 简洁性** |
| **消除偏见** | `Do NOT favor longer responses. Quality > Quantity.` |
| **结构化输出** | 要求 JSON：`winner` / `confidence` / `reason` / `category` |
| **温度归零** | `temperature: 0.0` —— 保证评判可复现 |

### 评估指标及格线

| 指标 | 及格 | 优秀 |
|---|---|---|
| **微调胜率**（微调胜 / 有效条数） | > 50% | > 65% |
| **Bad Case 率**（变差 / 有效条数） | < 20% | < 10% |
| 平局率 | 无标准 —— **但过高说明效果不显著** | |

### Bad Case 五分类（**判断时按这个分**）

| 类型 | 表现 | 严重度 | 常见原因 |
|---|---|---|---|
| **回答变差** | 逻辑混乱、不准确 | 🔴 高 | 训练数据里有错误信息 |
| **拒绝回答** | 原本能答的，微调后答不了 | 🔴 高 | LoRA 覆盖了基座的正确知识 |
| **过度拟合** | 所有回答都往训练数据方向靠 | 🟡 中 | 训练数据领域太窄 |
| **格式混乱** | 重复、截断、格式变差 | 🟡 中 | 训练数据 output 格式不统一 |
| **轻微偏差** | 方向偏了但不严重 | 🟢 低 | 训练数据风格影响 |

## 三 · 方法

### 输入

| 项 | 值 |
|---|---|
| Prompt 集 | `datasets/alpaca-clean-500条/my_test_dataset.json`（**50 条**，与训练集无重叠，已验） |
| 模型 A | 对照组（例如：基座 `Qwen3-8B` 未微调） |
| 模型 B | 实验组（例如：E04 某一组的 LoRA 适配器） |
| 推理方式 | Ollama 或任何 OpenAI 兼容端点（vLLM 等） |

> 📌 **同一条 prompt 必须原样喂给两边**，不做任何改写。

### 产出

| 文件 | 内容 |
|---|---|
| `results/comparison_samples.json` | 结构化：每条含 prompt / A 回答 / B 回答 / 非空标记 / 是否逐字相同 |
| `results/comparison_samples.md` | **人看的对照表**，留空「判断」列供逐条填 |

### 人工判断口径（逐条填）

每条只填一个值：

| 值 | 含义 |
|---|---|
| `A` | A 明显更好 |
| `B` | B 明显更好 |
| `both_good` | 都好，难分高下 |
| `both_bad` | **都差**（答非所问 / 空 / 明显错误） |
| `skip` | 无法判断（题目本身有歧义等）——**要写理由** |

> ⚠️ **`both_bad` 和 `both_good` 必须分开记。** 混在一起算「平局」，
> 就会重复 `results/` 那次评测的错误（20 条 `both_bad` 被算成打平）。

## 五 · 已知的局限（**必须写**）

### ⚠️ 还要防一个**代码级**的坑：胜率分母

`scripts/eval/evaluate.py` 第 217–220 行：

```python
valid_total = total - stats.get("ERROR", 0)               # ← 算出来了
stats["base_win_rate"] = f"{stats['A']/total*100:.1f}%"   # ← 却除以 total
stats["tuned_win_rate"] = f"{stats['B']/total*100:.1f}%"  # ← 却除以 total
```

**`valid_total` 算出来之后从未被使用** —— 胜率分母用的是 `total`，
**把 ERROR 也算进去了**。这会让胜率被系统性稀释。

👉 E05 的口径：**分母只能用「有效可判条数」**，并把 `valid_total` 真正用上。

### 其它局限

- **样本量小**（50 条），且来自一个数据集，**不能外推到所有 LoRA 任务**
- **人工判断是主观的**：单人判断、无第二人复核 → **不计算一致性系数**
  - ⛔ 因此**不要**把结果说成「统计显著」
- **评测集本身有缺陷**：`datasets/alpaca-clean-500条/` 的数据卡 §五-1 记录了抽样偏倚
  （取连续前 550 条，`instruction` 均长偏出总体 +31%）
- 判断只看**回答质量**，不看延迟 / 成本

## 六 · 怎么跑

```bash
# 1. 生成对照样本（同一条 prompt 喂给两个模型）
python scripts/eval/make_comparison_samples.py \
    --prompts datasets/alpaca-clean-500条/my_test_dataset.json \
    --model-a qwen3:8b \
    --model-b qwen3:8b-e04-a \
    --backend ollama \
    --out results/comparison_samples

# 2. 打开 results/comparison_samples.md，逐条填「判断」列
#    填完把统计结果回填到本文件 §四

# 3. 如果脚本报出「逐字相同」的条数 > 0 —— 先排查，不要往下走
```

> ⚠️ 脚本会打印三道检查的结果。**只要有 `ERROR` 或「逐字相同」异常，先排查再判。**
